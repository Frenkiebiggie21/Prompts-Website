Part 1: Questions for Clients

I questioned whether my initial questions were focused enough. I refined them to prioritise questions whose answers could significantly affect the product, such as business priorities, user relationships, existing systems, and the 10-week constraint, rather than asking many low-impact questions.

02

Part 2: Breaking Down the Problem

I modified my initial model by separating confirmed requirements from assumptions. For example, I avoided assuming that managers investigate security incidents or that property owners are users before the requirement was introduced. This made the model more realistic while keeping my original user, workflow, and system breakdown.

03

Part 3: Version One

I modified my original decision to leave security reporting completely out of V1. Since the scenario explicitly requires tenants to report security issues, I included basic security reporting while still leaving more advanced security functionality for later. I kept my original focus on maintenance and the 10-week constraint.

One Piece of AI-Generated Advice I Modified

The clearest example was Part 3. I originally planned to postpone security incident management entirely. I modified that decision after the AI pointed out that security reporting was explicitly stated as a client requirement. Rather than accepting the idea of building a complete security-management system, I chose a smaller basic security-reporting feature for V1 and left more advanced functionality for later.

This was useful because I wasn't simply accepting or rejecting the AI's suggestion; I used it to challenge my original assumption and then made my own prioritisation decision.

04

Part 4: New Owner Requirement

I questioned the idea that adding property owners simply meant adding another user role. I modified my thinking to recognise that ownership changes the relationship between users and buildings, which can affect permissions, data relationships, reports, and testing.

05

Part 5: Existing System Investigation

I questioned the assumption that the database must be the source of the problem. I kept my original approach of reproducing and tracing the issue, but expanded it to follow the status through the entire process: manager action → stored data → service/API → tenant application → displayed status.

06

Part 6: AI Recommendation

I questioned the recommendation to create separate databases for each user type. I did not reject it immediately; instead, I wanted to compare it with a shared database using appropriate access controls and understand the effects on reporting, data consistency, security, maintenance, and future growth.

07

Part 7: Client Communication

I modified my original explanation to make it more direct and less technical. I kept the same recommendation but focused more on what the client gets, why it matters, what is being postponed, and what we still need from them.
